# 수정 지침 — 학기 상한을 학년 기준(1·2학년 20 / 3·4학년 18)으로, 커리어개발은 상한 밖 +1

> 이 문서는 AI 개발 에이전트가 **그대로 읽고 처리**하도록 쓴 작업 지시서다.
> 프로젝트: 「아 맞다, 인생!」(한양대 정보시스템학과 플래너) — Next.js App Router + TypeScript + Tailwind v4.
> 작업 전 `CLAUDE.md`, `docs/PLAN.md`를 읽는다. 엔진(`src/engine/**`)은 순수 함수다: React·fetch·DB 금지.

## 0. 사용자 요구 (원문 요지)

1. 지금 학기 카드의 **“/ 상한 N”이 제멋대로**다(스크린샷: 2027 1·2학기 상한 18, 2028 1·2학기 15, 2030-2·2031-1·2031-2 12).
2. **1·2학년 학기는 최대 20학점 → 상한 20.** **3·4학년 학기는 최대 18학점 → 상한 18.**
3. **커리어개발 과목**은 총학점에는 포함되지만 **학기 최대학점(상한) 조건을 받지 않는다** → 그 학기에 1학점을 상한 위로 그냥 더할 수 있다.
4. 커리어개발은 **1학년 1학기**(커리어개발Ⅰ)와 **3학년 2학기**(커리어개발Ⅱ)에 듣는다 → **1학년 1학기 상한 21**, **3학년 2학기 상한 19**.

## 2. 바꿀 규칙 (정확한 정의)

### 2.1 학년 판정

- **학년 = 유효학기 순번(ordinal)** 기준. ordinal = `input.completedTerms + (이번 계획에서 앞서 다닌 수강 학기 수) + 1`. 군 복무·휴학·교환(중단) 학기는 세지 않는다(지금 카드의 “유효학기 n”과 같은 값).
- ordinal 1~4 → **1·2학년 → 기본 상한 20**.
- ordinal 5 이상 → **3·4학년(5학년 이상 초과학기 포함) → 기본 상한 18**.
- 1학년 1학기 = ordinal 1, 3학년 2학기 = ordinal 6.

### 2.2 커리어개발 예외(상한 밖 가산)

- 커리어개발 과목 집합: `GEN5029`(커리어개발Ⅰ), `GEN5100`(커리어개발Ⅱ). **코드 목록을 엔진 상수 한 곳**(예: `src/engine/pace.ts`의 `CAP_EXEMPT_COURSES`)에 두고, 이름 문자열 매칭으로 판정하지 않는다.
- 어떤 학기에 커리어개발 과목이 배치되면 **그 학기 상한 = 기본 상한 + 그 학기 커리어개발 학점 합**.
  - 1학년 1학기(ordinal 1)에 GEN5029(1) → **20 + 1 = 21**.
  - 3학년 2학기(ordinal 6)에 GEN5100(1) → **18 + 1 = 19**.
- 가산된 1학점은 **커리어개발 과목만** 쓸 수 있다. 다른 과목·전공 선택 자리·미지정 자리·교양 자리가 이 1학점을 쓰면 안 된다. 구현: 커리어개발 과목은 `used`(상한 비교용)에 넣지 않고 따로 `exemptUsed`로 센다. 다른 과목 배치 판정은 `used + c.credits <= baseCap`.
- 커리어개발 학점은 **총학점·누적학점·남은 학점(remaining)·학기 합계(plannedCredits)에는 포함**한다(사용자 요구: “학점에 포함되지만”).
- 이미 이수한 학생(`completedCourseCodes`에 있음)은 배치하지 않으므로 가산도 없다 → 상한은 기본값(20/18).
- 사용자가 피드백으로 뺀 경우(`courseRules` exclude)도 배치 안 함 → 가산 없음.

### 2.3 커리어개발 배치 (지금은 아예 안 들어가므로 새로 넣는다)

- 커리어개발 과목은 진로와 무관하게 **모든 학생 공통 필수(교양필수)** 로 배치 대상에 넣는다. 방법(둘 중 하나, 권장 1):
  1. `simulatePlan`에서 `recommendedCourses()` 결과에 `CAP_EXEMPT_COURSES` 중 데이터셋에 있는 과목을 더한다(진로 추천 `careerTags`는 건드리지 않음 — 서비스 진로 분류와 학교 필수를 섞지 않기 위해).
  2. 또는 fixture `careerTags`에 `group: "common"`으로 추가 — 이 경우 `scripts/normalize/validate-fixture.ts` 통과 확인, 진로 화면 ‘공통 기초’ 범례에 섞여 보이는지 확인.
- 배치 학기: 자료의 `recommendedYear`/`semester` 그대로(커리어개발Ⅰ = 1학년 1학기, 커리어개발Ⅱ = 3학년 2학기). 기존 배치 규칙(`recommendedYear > studentYear`면 건너뜀, `semester !== term.season`이면 건너뜀)을 따른다.
  - 이미 1학년 1학기를 지난 학생(예: 2학년부터 계획)은 커리어개발Ⅰ이 **처음 맞는 1학기**에 들어간다 → 그 학기도 상한 +1(규칙 2.2는 “커리어개발이 배치된 학기”에 적용되므로 자연히 맞다). 화면 경고 한 줄: “커리어개발Ⅰ은 1학년 1학기 과목인데 아직 이수 기록이 없어 {학기}에 넣었어요. 이수했다면 이수 현황에서 체크하세요.”
- 개설 종료연도 이후 배치(GEN5029 offeringEndYear 2027)는 기존처럼 `offering_after_end_year` 가정 표시(빨간 “가정”)를 단다.
- 커리어개발은 **전공이 아니다**(교양필수). `isMajorCourse`에 걸리지 않으므로 전공학점·전공 요건 계산에 들어가지 않는지 테스트로 확인.

### 2.4 계획 학점(페이스)과의 관계

- **상한(capCredits)**: 2.1 + 2.2로 정한 학교 기준 최대값. 화면 “/ 상한 N”은 **이 값만** 보여 준다.
- **계획 학점(plannedCredits)**: 지금처럼 사용자 페이스(15/18/20, 후반 여유형 구간, 피드백의 학기별 제한 `termCaps`)를 따르되 **상한을 넘지 않는다.**
  - 학기의 실제 배치 한도 = `min(userCapFor(...)[페이스], termCaps[사용자 학기 제한], baseCap[학교 기본 상한])` + 커리어개발 학점.
  - 예: 페이스 18인 1학년 1학기 → 계획 18 + 커리어개발 1 = 19, 화면 “합계 19 / 상한 21”.
  - 예: 페이스 20인 1학년 1학기 → 20 + 1 = 21, “합계 21 / 상한 21”.
  - 예: 페이스 20인 3학년 1학기 → 학교 상한 18이 이김 → “합계 18 / 상한 18”.
  - 예: 후반 여유형으로 7번째 학기 12 → “합계 12 / 상한 18”(상한은 학교 기준이라 18 그대로).
- 사용자 페이스 상한이 따로 보여야 한다면 카드 아래 작은 회색 글씨로 “내 계획 18학점”처럼 **다른 이름**으로 구분해 표시(선택). “상한”이라는 단어는 학교 기준에만 쓴다.
- `PlannedTerm`에 필드 추가(이름 예시):
  - `capCredits`: 학교 상한(가산 포함) — 의미 변경. 기존 소비처(Roadmap, PrintPlan, tracks, MatchResults, TrackDetail, stats, evidence, OutputScreen의 상한 문구) 전부 확인.
  - `baseCapCredits`: 가산 전 학교 기본 상한(20/18).
  - `capExemptCredits`: 커리어개발로 더한 학점(0 또는 1).
  - `planLimitCredits`: 페이스·사용자 제한까지 반영한 이 학기 계획 한도(커리어개발 제외).
  - `capRuleId`: 적용한 상한 규칙 id.
  - 타입 변경은 `src/contracts/types.ts`에서 하고 **mock(`src/contracts/mock-plan.ts`)·fixture·테스트를 같은 PR에서** 고친다(CLAUDE.md).

### 2.5 최소 신청학점(기존 유지)

- `schoolMinFor`(1~7번째 학기 10학점, S2 17~18쪽) 동작은 그대로. 최소학점 채우기 계산에서 커리어개발 학점도 학기 합계에 포함된다(합계 기준).

## 3. 학교 자료·출처 처리 (CLAUDE.md “확인되지 않은 학교 수치를 만들지 않는다”와의 관계)

- 20/18 숫자의 근거: **S2(2026-2 수강신청 안내문) 17~18쪽**. 다만 fixture에서 2026학번 이후 20/18은 `status: "planned"`(“조정 예정”)이고, 2025학번까지는 `S2-P17-CAP-2025`로 1~7번째 학기 모두 20(verified)이다.
- 사용자(제품 담당)가 **“1·2학년 20, 3·4학년 18”을 서비스 규칙으로 쓰라고 명시적으로 결정**했다. 따라서:
  1. 학년 기준 상한을 **입학연도와 무관하게, 입학연도 미입력이어도** 적용한다.
  2. 규칙 데이터를 바꾼다: `creditCapRules`에 서비스 적용용 규칙 2개를 둔다(예: `CAP-GRADE-1-2` ordinal 1~4 / 20, `CAP-GRADE-3-4` ordinal 5~ / 18). `sourceRef`는 S2 17·18쪽, `appliesTo.note`에 “S2 안내(2026학년도 신입생 기준 예정 안내)를 서비스 계획 기준으로 전 학생에 적용 — 2025학번 이전 현행표(7번째 학기까지 20)와 다를 수 있음”을 적는다. 상태값을 새로 만들어야 하면(`ConfirmStatus`에 없는 값) 새 값 대신 `appliesTo.note`와 화면 문구로 구분하고, `schoolCapFor`가 이 두 규칙을 쓰도록 바꾼다. 기존 3개 규칙은 근거 기록으로 남기되 상한 계산에는 새 규칙만 쓴다(중복 적용 금지).
  3. 커리어개발 예외(+1)도 사용자 결정 규칙이다. 원문 쪽수가 확인되지 않았으므로 코드 주석·`appliesTo.note`·화면 출처 문구에 **“서비스 기준(사용자 확인) — 학교 안내문 쪽수 미확인”**으로 표시한다. 숫자를 S2에서 확인된 것처럼 쓰지 않는다.
  4. 2025학번 이전 학생에게 3·4학년 18은 실제 학교 기준(20)보다 보수적이다 → 결과 화면 ‘가정한 것·확인 필요’에 한 줄 경고: “3·4학년 18학점 상한은 2026학년도 신입생 기준 안내를 적용했어요. {입학연도}학번은 수강신청 안내문 17쪽 현행 기준(20학점)일 수 있어요.” (입학연도가 2025 이하일 때만.)
- `docs/data-sources.md`(자료 사전)에 새 규칙 id와 근거·적용 범위를 한 줄씩 추가.
